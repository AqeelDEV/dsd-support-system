# Security review

A review of the whole system against the SRS's security requirements (NFR-5 to NFR-9) and the OWASP Top 10 (2021), done on 3 October 2026 before release. It records what protects each area, the tests that try to get past it, what the review found and how each finding was fixed. The design behind it is in [ARCHITECTURE.md](ARCHITECTURE.md#security-boundaries) and the ADRs it links to.

## How the review was done

- Read every boundary a request crosses: the web apps' proxy, the API's guards, the services' resource checks, the database roles, the worker and the object store.
- For each OWASP category, listed what could go wrong in this system, and checked the code and the test that should stop it.
- Ran `pnpm audit` on the dependency tree and gitleaks on every commit in the history.
- Wrote a test for every fix, so none of them can quietly come undone.

Advisories reviewed and not fixed, each with its reason:

- **braces, GHSA-vfj7-8cjw-p6xm** (high, no fixed version): stack exhaustion on deeply nested patterns. It reaches us only through fast-glob in the Next.js ESLint plugin, at lint time, on this repository's own patterns. It ships in no image and never sees user input. It is ignored in `pnpm-workspace.yaml` with this reason, so any new high advisory still fails CI.
- **esbuild, GHSA-67mh-4wv8-2f99** (moderate): its development server accepts cross-origin requests. It comes in through drizzle-kit, which never starts that server; it is a build tool for migrations and isn't in any image. It is below CI's threshold and listed here.

## NFR-5 to NFR-9

| Requirement                                            | How it holds                                                                                                                                                                                                                                                                                                                                                                                    | Tests                                                                                                                          |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| NFR-5: credentials hashed, never logged                | Passwords: argon2id at the OWASP baseline (19 MiB, 2 iterations), with a dummy hash for unknown accounts so timing doesn't reveal them, and rehashing when parameters rise. Session and emailed-link tokens: 32 random bytes, stored as SHA-256. Logs never hold headers, bodies or query strings, and pino redacts password, token, cookie and authorization fields in the API and the worker. | unit: `password-hasher`, `tokens`; int: `auth-logging`, `logging`; worker int: `ai-pipeline` (no ticket text in logs)          |
| NFR-6: every state change authenticated and authorised | A global deny-by-default guard; the API won't start if a route lacks an access rule. Permissions are checked by a guard and by resource checks in the services. The RBAC matrix calls every route as 10 actors.                                                                                                                                                                                 | rbac: `rbac-matrix`, `route-coverage`; int: `route-access`, `realms`                                                           |
| NFR-7: input validated, output escaped                 | Strict zod schemas at the boundary (unknown fields refused). React escapes text, and `dangerouslySetInnerHTML` is banned by lint. Markdown is sanitised on save and rendered as React elements. Emails escape every value. A nonce-based CSP with `strict-dynamic`. AI drafts are plain text, and their links are checked (finding 7).                                                          | unit: `boundaries`, `markdown` (shared and ui), `templates`, `suggestion-draft`; e2e: `customer/xss`, `agent/xss`; smoke (CSP) |
| NFR-8: uploads checked by content, capped, private     | Magic bytes against an allowlist, plain text decided by a strict rule, 10 MB and 5 files. Random keys in a private bucket. Downloads only through an endpoint that checks access, with `Content-Disposition: attachment`, `nosniff` and a sandboxing CSP.                                                                                                                                       | int: `attachments`, `attachment-intake`; unit: `content-check`; smoke (headers through the proxy)                              |
| NFR-9: rate limits on submission and sign-in           | Redis-backed fixed windows keyed by an HMAC of the address or email. Sign-in and emailed links refuse when Redis is down; ticket submission, search and replies stay open. The client address is the browser's, through the trusted proxy (ADR-0010).                                                                                                                                           | int: `rate-limits`, `public-rate-limits`, `rate-limiter`; unit: `client-address`; smoke (forged header)                        |

## OWASP Top 10 (2021)

| Category                        | In this system                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A01 Broken access control       | Separate customer and staff realms with separate cookies and proxies. A central permission map, and resource checks so a customer sees only their own tickets and a guest only one. Brand scope on staff queries. Internal notes filtered in the query and absent from customer schemas. Least-privilege database roles. All of it is tested by the matrix, the route-coverage test, and the `internal-notes`, `privileges` and `ai-guardrail` tests. |
| A02 Cryptographic failures      | argon2id for passwords; SHA-256 for 256-bit tokens; HMAC-SHA256 for CSRF tokens and rate-limit keys, with keys derived from `AUTH_SECRET`. `__Host-`, `Secure`, `HttpOnly`, `SameSite=Lax` cookies. HSTS in production. TLS is the deployment's front door; the Compose stack is local HTTP by design.                                                                                                                                                |
| A03 Injection                   | Parameterised queries throughout, through Drizzle and `pg`. Two places build SQL text, both safe by construction: the report's duration helper takes column names fixed in code, and the test harness checks database names against a strict pattern. Prompt injection is treated as a given, not prevented: ticket text is escaped and delimited, and whatever a model writes is a draft that is checked and never sent by itself.                   |
| A04 Insecure design             | The AI can't send anything: no code path, no database privilege, one entry point that needs an agent's session, approval constraints in the database. Every ticket change goes through a state machine with history in the same transaction. A transactional outbox means a failed email can't lose or duplicate a change.                                                                                                                            |
| A05 Security misconfiguration   | Config is validated at startup; the API refuses insecure cookie settings and the published development secret outside localhost. Helmet with a strict CSP for Swagger UI; frame-ancestors `none` everywhere. Containers run as the unprivileged `node` user, and data stores bind to 127.0.0.1. Swagger UI stays on at `/api/docs` (decision below).                                                                                                  |
| A06 Vulnerable components       | `pnpm audit` in CI at high severity, a frozen lockfile, packages pinned to releases at least a day old, actions pinned to commits. Finding 1 fixed the outstanding advisories.                                                                                                                                                                                                                                                                        |
| A07 Authentication failures     | Rate limits per address and per email, with no permanent lockout. Sign-in always creates a new session and revokes the old one. Sign-up, guest links and password reset answer the same whether or not an account exists. Sessions expire absolutely and when idle, and a deactivated agent's session fails at once. Emailed links work once and expire.                                                                                              |
| A08 Software and data integrity | Frozen-lockfile installs, CI on every push, commits checked by commitlint. History tables are append-only and ticket fields write-once, enforced by database triggers. Seeded and uploaded files carry a SHA-256.                                                                                                                                                                                                                                     |
| A09 Logging and monitoring      | Structured JSON logs with request IDs, and worker logs carrying event and job IDs. An audit event for every ticket change, made in the same transaction. Dead-letter queue with a CLI. Logs never hold credentials or message bodies. Metrics and tracing are in the scaling plan.                                                                                                                                                                    |
| A10 Server-side request forgery | Nothing fetches a URL a user supplies. The web apps' proxy has a fixed upstream, an allowlist of path prefixes, refuses encoded separators and doesn't follow redirects. AI provider URLs come from configuration only. External images in articles are shown as links.                                                                                                                                                                               |

## Decisions

- **Swagger UI stays on at `/api/docs`, also in production builds.** It documents only the contract the routes already enforce, and every route still applies its own access rule. Reviewers use it in the Compose stack. Hiding it would be obscurity, not access control. A deployment that wants it off can block the path at its edge.
- **Gemini's free tier is for synthetic data only.** Google may use free-tier prompts to improve its products, so real tickets need the paid tier or another provider under a data-processing agreement ([ADR-0006](adr/0006-ai-suggestions-and-guardrail.md)). The default provider is the offline mock, and no ticket text leaves the machine unless a key is set.
- **Redis has no password in the Compose stack**; it listens on the stack's private network and 127.0.0.1 only. A deployment uses an authenticated, TLS-terminated Redis (ElastiCache, for instance).

## What is not covered

- No antivirus scanning of uploads ([ADR-0009](adr/0009-attachments.md)): files are checked by type and never served inline, but a malicious PDF can still reach an agent who downloads and opens it.
- No penetration test by a third party, and no fuzzing beyond the tests listed here.
- No web application firewall or bot detection; rate limits are per address and per account, which a distributed attack can spread across.
- Safari wasn't available to test the local cookie mode on this Windows machine; it was checked in Chromium and by the cookie attributes the API sends.
