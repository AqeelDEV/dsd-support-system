# Requirements traceability

Every requirement in the [SRS](SRS.md) (FR, NFR, UI and API) is listed here with the phase that delivers it, where it will live in the code, and the test that proves it. The table is updated at the end of every phase, so it always shows what is designed, what is built and what is proven.

## How to read this

### Phases

| Phase | Name                                                               | Scope                                                                                                 |
| ----- | ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| 0     | Plan and design                                                    | Architecture, data model, ADRs, this document                                                         |
| 1     | Foundations                                                        | Monorepo, tooling, Docker Compose, API and worker skeletons, web app skeletons, CI                    |
| 2     | Data model                                                         | Drizzle schema, migrations, triggers, constraints, database roles, seed framework                     |
| 3     | Authentication and RBAC                                            | Realms, sessions, CSRF, rate limits, guest access, permission map, RBAC matrix and route coverage     |
| 4     | Ticket core API                                                    | Tickets, messages, internal notes, status, priority, assignment, escalation, audit trail, attachments |
| 5     | Knowledge base, canned responses, reporting, agent management APIs |                                                                                                       |
| 6     | Events, queues and notifications                                   | Outbox dispatcher, BullMQ queues, retries, dead-letter queue, email notifications                     |
| 7     | Customer web app                                                   |                                                                                                       |
| 8     | Agent and supervisor web app                                       |                                                                                                       |
| 9     | AI-assisted responses                                              | Synthetic knowledge base, indexing, hybrid retrieval, suggestions, guardrail, evaluation              |
| 10    | Hardening                                                          | Security review, performance with 5,000+ tickets, accessibility, end-to-end suite                     |
| 11    | Documentation and final audit                                      | README, final traceability check, fresh-clone test                                                    |

### Status values

- **Designed**: covered by the Phase 0 design documents.
- **Implemented**: the code is merged.
- **Partly verified**: the part delivered so far is built and its proving tests pass in CI. Later phases complete the rest, as the row says.
- **Verified**: the proving tests pass in CI.

### Shorthand

| Written as      | Means                                                                                                     |
| --------------- | --------------------------------------------------------------------------------------------------------- |
| `api/<module>`  | `apps/api/src/modules/<module>` (and `api/auth` is `apps/api/src/auth`)                                   |
| `worker/<part>` | `apps/worker/src/<part>`                                                                                  |
| `db`            | `packages/db`                                                                                             |
| `shared`        | `packages/shared`                                                                                         |
| unit: `name`    | Unit test `name.spec.ts` next to the code                                                                 |
| int: `name`     | Integration test `test/integration/name.int.spec.ts` in the relevant app, against real Postgres and Redis |
| db: `name`      | Database test in `packages/db/test/`                                                                      |
| rbac: `name`    | Test in `apps/api/test/rbac/`                                                                             |
| e2e: `name`     | Playwright test in `e2e/`                                                                                 |

Test names are planned names. If a phase ends up using a different name, it updates this table.

## SRS notes and interpretations

Where the SRS is ambiguous or inconsistent, this is how it is read. Each interpretation is recorded in an ADR.

1. **FR-14** says "RBAC, see NFR-3", but NFR-3 is the 100x-scale note. It is read as a reference to NFR-6, which covers RBAC enforcement.
2. **FR-6** says "see NFR-6", but NFR-6 is about endpoint authorisation. It is read as a reference to §5 (Channel as an attribute of Ticket) and §11.2 (omnichannel intake).
3. **UC-6 (escalate a ticket)** has no functional requirement. It is implemented as an explicit escalate action ([ADR-0007](adr/0007-ticket-lifecycle.md)).
4. **The System Administrator** in §2.3 is covered by the `admin` role. v1 has no integrations or system settings to configure beyond agent and role management ([ADR-0004](adr/0004-authorization-rbac.md)).
5. **SLAs.** §2.3 mentions supervisors managing SLAs, but SLA workflows are out of scope (§10). v1 reports response and resolution times (FR-13) without SLA targets.
6. **"A contact method"** in FR-1 is the customer's email address, the only notification channel in v1 ([ADR-0007](adr/0007-ticket-lifecycle.md)).
7. **Reporting averages** (FR-13) are computed in calendar time, with medians shown alongside ([ADR-0007](adr/0007-ticket-lifecycle.md)).
8. **Language.** Multi-language support is out of scope (§10). Full-text search uses the `english` configuration; a per-brand language setting is the extension point.

## Delivery log

What each phase delivered and which tests prove it. Test names follow the shorthand above; every test listed runs in CI on every push.

### Phase 1: Foundations

Built:

- A pnpm and Turborepo workspace with strict TypeScript, ESLint, Prettier, commit hooks and a GitHub Actions pipeline.
- The API skeleton: validated configuration, request IDs, structured logging with redaction, RFC 9457 problem details, the `/api/v1` prefix, security headers, a CORS allowlist, `/health`, `/ready`, and an OpenAPI 3.1 document with Swagger UI.
- The worker skeleton: an explicit composition root, a bounded wait for its dependencies at startup, and a clean shutdown.
- Both web app skeletons with the shared theme, security headers and a realm-scoped API proxy.
- One Docker Compose stack for everything, started with one command.

Proven:

| Test                                                    | Proves                                                                                                    |
| ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| unit: `boundaries` (config)                             | Each ADR-0002 dependency rule fails a deliberate violation; `dangerouslySetInnerHTML` is rejected         |
| int: `health` (api)                                     | `/ready` is `ok`, `degraded` (200) without Redis and 503 without PostgreSQL; `/health` needs neither      |
| int: `http-conventions` (api)                           | Problem details with request IDs, request-ID handling, `/api/v1` versioning, security headers, CORS, docs |
| int: `logging` (api)                                    | Request logs carry the request ID and no cookies, tokens, query strings or bodies                         |
| unit: `problem-details`, `env`, `request-id` (api)      | Error mapping never leaks server errors; bad configuration is refused without echoing values              |
| unit: `proxy` (api-client), `api-proxy` (both web apps) | Each app forwards only its own realm's routes, including against `..` and encoded-separator tricks        |
| int: `lifecycle` (worker)                               | The worker starts as `dsd_worker`, stops cleanly and gives up clearly when PostgreSQL stays down          |
| CI `compose-smoke`                                      | The whole stack starts from a clean checkout with one command and answers as documented                   |

### Phase 2: Data model

Built:

- The Drizzle schema for every table, enum, constraint and index in the [data model](DATA_MODEL.md), with the enum values shared with the API through `packages/shared`.
- Four migrations: the extension guard, the generated schema, the history and integrity triggers, and the role grants.
- A migration runner and a compose `migrate` service that runs it, and the seed, before the API and worker start.
- A deterministic seed: one brand, demo accounts for every role, synthetic staff and customers, and 60 tickets with consistent histories.
- A test harness that creates a fresh, migrated database per test file on real PostgreSQL.
- A lint rule that stops the worker importing the `messages` table, and a CI check that the schema and the committed migrations agree.

Proven:

| Test                              | Proves                                                                                                                      |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| db: `migrations`                  | Migrations apply from zero and are idempotent; the tables, CHECK constraints and triggers match the names in the data model |
| db: `append-only`                 | `messages` and `audit_events` refuse UPDATE, DELETE and TRUNCATE by trigger for the owner and by privilege for the API      |
| db: `tickets`                     | References are built by the database and never truncated; every write-once field refuses a change                           |
| db: `constraints`                 | Every CHECK constraint rejects a row built to break it; a reply can't use another ticket's suggestion; unique keys hold     |
| db: `privileges`                  | Both roles' privileges match the matrix exactly; the worker can't write messages, tickets or audit events                   |
| db: `seed`, unit: `generate` (db) | The seed is deterministic, covers every status and priority, writes no outbox events and hashes with argon2id               |
| db: `indexes`                     | Each documented query is served by its index, and ordered queries need no sort                                              |
| unit: `boundaries` (config)       | Every form of importing `messages` from the worker fails the lint                                                           |
| unit: `enums` (shared)            | The enum values match the data model value for value and in order                                                           |
| CI `db:check`, CI `compose-smoke` | Schema and migrations agree; the stack migrates and seeds from zero with one command                                        |
